## 2. Violation details

### V-01: Owner references use RESTRICT, and notifications have a foreign key to boards

| Field | Details |
|---|---|
| Guideline broken | DB-CAS-01 in `database.md` |
| Rule (short, in my words) | Owner and author references (`created_by`, `added_by`, `assignee_id`) must be `ON DELETE SET NULL`. `notifications.board_id` must have no foreign key. |
| Location in generated code (baseline `e3fbedd`) | `backend/app/models/board.py:17` (`owner_id`, RESTRICT); `backend/app/models/card.py:22` (`created_by`, RESTRICT); `backend/app/models/comment.py:17` (`user_id`, RESTRICT); `backend/app/models/notification.py:17` (`board_id`, FK CASCADE) |
| Also affects | DB-OWN-01, DB-NTF-01 |
| Severity | Medium. Deleting a user who owns a board, created a card or wrote a comment fails with a foreign key error. Deleting a board removes notifications that should survive. |
| How I found it | Manual review of the baseline models, plus `grep -rn "ForeignKey" backend/app/models/`. |

**What Kiro generated (baseline):**

```text
# backend/app/models/card.py
created_by = db.Column(
    UUID(as_uuid=True),
    db.ForeignKey("users.id", ondelete="RESTRICT"),
    ...
)
# backend/app/models/notification.py
board_id = db.Column(
    UUID(as_uuid=True),
    db.ForeignKey("boards.id", ondelete="CASCADE"),
    ...
)
```

**Why this violates the guideline:** DB-OWN-01 says deleting a user must not block on the work they created, and a NULL `created_by` means "no owner". RESTRICT blocks the user delete. The board-level FK on notifications makes the notification disappear with its board, which DB-NTF-01 forbids.

**Refinement prompt I wrote:** see the database refinement prompt in section 0.

**Fix applied (V4 model excerpt, `e1abc90`):**

```text
# backend/app/models/card.py
created_by = db.Column(
    UUID(as_uuid=True),
    db.ForeignKey("users.id", ondelete="SET NULL"),
    nullable=True,
)
# backend/app/models/notification.py: no ForeignKey on board_id
board_id = db.Column(UUID(as_uuid=True), nullable=True)
```

| Field | Details |
|---|---|
| Fix commit | `e1abc90` (models), `c18264f` (migration `0002_v4_schema`) |
| Fixed by | Regeneration (sub-agent), not a manual edit |
| How I verified the fix | `pg_constraint` on `revotask_db` shows `fk_cards_created_by_users ... ON DELETE SET NULL` and `fk_cards_assignee_id_users ... ON DELETE SET NULL`, and the composite `(column_id, board_id)` FK with `ON DELETE CASCADE`. The cascade tests in `backend/tests/database/test_cascades.py` pass. |

### V-07: A member can delete a column that holds other members' cards

| Field | Details |
|---|---|
| Guideline broken | BE-AZ-04 in `backend.md` (also BE-STR-02 for the role check that moved into the service, and DB-CAS-02 for the cascade safety net) |
| Rule (short, in my words) | A Member may delete a column only if they created it and every card inside it was created by them. Otherwise the request returns 409 `COLUMN_HAS_FOREIGN_WORK`. |
| Location in generated code (baseline) | `backend/app/blueprints/columns/service.py:56-59` (`delete_column` soft-deletes the column with no check on the cards) |
| Also affects | BE-AZ-02 (the permission matrix) |
| Severity | High. The database cascade would silently destroy other members' cards, which is the data-loss case the steering was written to block. |
| How I found it | Scored check 9 on the baseline. Read `delete_column` in full. |

**What Kiro generated (baseline):**

```text
def delete_column(access: ColumnAccess) -> dict[str, Any]:
    """Soft-delete the column only; its cards stay untouched (Req 7.4)."""
    column.soft_delete()
```

**Why this violates the guideline:** there is no foreign-work check, so any Member who can see the board can remove a column and its cards, including other members' work. The soft delete also disagrees with DB-CNV-05 (columns are hard-deleted).

**Refinement prompt I wrote:** see the backend refinement prompt in section 0 (rule: "Member column delete returns 409 COLUMN_HAS_FOREIGN_WORK").

**Fix applied (`bf06496`):** `backend/app/blueprints/columns/service.py:108-121` checks every card's `created_by` for a Member. Any card with a different or null `created_by` returns 409 `COLUMN_HAS_FOREIGN_WORK` with `details: {"cards": n}`. Admins skip the check. The column is hard-deleted, and the cascade runs only after the check passes.

A later leftover from the same rule (a role comparison and a `db.session` call in `boards/routes.py`) was fixed by hand in `1935b07`. It moved the member email check into `boards/service.py::member_row`.

| Field | Details |
|---|---|
| Fix commit | `bf06496` (column rule), `1935b07` (routes leftover) |
| Fixed by | Regeneration (sub-agent) for the column rule. The routes leftover was a manual edit by me, after the sub-agent's regeneration. |
| How I verified the fix | Test `test_delete_column_with_foreign_card_409` and the role matrix in `backend/tests/api/test_cards.py` and `test_columns.py` pass. `grep -rn "db.session\|== \"admin\"" backend/app/blueprints/*/routes.py` returns nothing. |
